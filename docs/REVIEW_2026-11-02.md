# AXLink — state and architecture review

Date: **2026-11-02** · Review: Claude Code (Opus 5.5)
Basis: the local project folder, GitHub, the pinned upstreams (Packet.NET, pdn-net), the F4HWN
branch `feature_update_v7`, the firmware fork `TechnikWeber/uv-k1-k5v3-aprs-firmware` (branch
`messenger`), and the law texts on gesetze-im-internet.de (retrieved 2026-11-02). Sources at
the end. Estimates are marked as such.

> **Addendum (2026-11-02):** the decisions taken after this review are in
> [`DECISIONS.md`](DECISIONS.md) and take precedence. Go is set. The software builds in **no**
> legal restrictions (operator responsibility); section 5.3 is therefore information only, and
> the operating profiles proposed there are dropped. The original German version of this review
> is in the git history.

## Summary

1. **The goal and the guardrails are right.** The test discipline of the Codex phase is good.
   **The technical base does not fit** the product: one app for Linux and Windows (macOS
   optional), tuned to our own firmware, with gateways.
2. There is **no AXLink product code yet**. Starting over costs little now and a lot later.
3. The existing demo is a chain of **three processes** (pdn node, pdn-net, lab script) in
   Docker and runs on Linux only. pdn-net has ~1,500 lines, was essentially written over one
   weekend in July 2026 and has three real defects (F1, F4, F5).
4. **The demo says little about real hardware.** The KISS app on the radio holds exactly **one**
   frame for transmission and has a **256-byte USB ring without back-pressure**. A full IP packet
   (MTU 256) is lost today if the host writes it in one go. The simulator does not model this.
5. **Recommended stack:** a new core as **one Go program** (`axlinkd`) with wireguard-go/tun
   (Linux, Windows, macOS), gVisor netstack (userspace TCP/IP for gateways and for running
   without admin rights) and go.bug.st/serial. We write KISS, AX.25 UI and IP over AX.25
   ourselves (small, well specified). Packet.NET/pdn stays a **peer in interop tests**, not a
   runtime dependency. C# would work too, but without a portable gateway.
6. **Internet gateway:** technically quite feasible. **Legally** narrow in German amateur
   radio: § 5 (5) AFuG (messages for third parties) and § 16 (8) AFuV (no encryption, hence no
   HTTPS over the air). Uncritical: **linking radio islands over the internet** (amateur to
   amateur), amateur-radio services, emergencies and disasters.
7. **Firmware:** small extensions of the KISS app (ACKMODE, identification, RSSI) and a USB fix
   in the resident firmware are what make IP on the Quansheng robust. Until then AXLink needs a
   strict TNC profile.

## 2. What is good and stays

- **Principles:** ordinary IP must work. Standard framing UI/PID `0xCC`. Simulation before
  radio. No transmission without a deliberate setup.
- **Test discipline:** pinned sources, a negative control (channel paused, the request must
  fail), the IP bytes must appear in the AX.25 trace on both sides, an isolated network. We keep
  this as it is.
- **Real upstream findings:**
  - F1: pdn-net delivers frames addressed to other stations to the TUN (no destination filter).
  - F4: pdn-net reads the segment header (PID `0x08`) differently from AX.25 2.2 figure 6.2 and
    from Packet.NET. Confirmed in the code: pdn-net takes bits 7–1 as the number and bit 0 as
    "last"; the standard takes bit 7 as "first" and bits 6–0 as the remaining count.
  - F5: fragmentation ignores DF and existing offsets.
  F1 and F4 should be reported to pdn-net.
- **net-sim** (Go; AFSK1200 in the audio domain, FM capture, collisions, ACKMODE) stays our test
  channel; it can be used from any language over KISS-TCP. Licence: the pinned image label says
  MIT, the GitHub repository now shows AGPL-3.0. Fix `LICENSING.md` accordingly (uncritical for
  test use only).
- **Legal guardrails** (as planned at the time): no encryption, no 44Net without an allocation,
  a broadcast filter.

## 4. Tuning to our firmware

### 4.1 What the KISS TNC app does today

Source: `App/apps/kisstnc/kisstnc_app.c`, `App/usb/usbd_cdc_if.c`, `App/apps/app_overlay.c`
(the same in v6.3 and v7).

- **Radio:** Bell 202 at 1200 Bd on the VFO frequency. Frequency, power and bandwidth are set on
  the radio. The app is started on the radio. It is **modal**: normal radio operation and the
  messenger pause while it runs.
- **KISS:** Data (0), TXDELAY (1, in 10 ms) and P (2) are honoured. SlotTime is fixed at 50 ms,
  TxTail at 3 flags; other commands are ignored. No ACKMODE, no identification.
- **Receive:** every AX.25 frame with a valid FCS goes to the host (FCS removed), without an
  APRS filter. An identical copy within 1 s is dropped. The RSSI is only shown on the screen.
- **Transmit:** exactly one frame can wait. Whatever the host sends meanwhile is dropped without
  being counted. The channel check uses only the app's own demodulator; it does not see a voice
  carrier. Defaults: TXDELAY 267 ms, P = 63.
- **Frame size:** at most 330 B including the FCS. Enough for MTU 256.
- **USB:** CDC-ACM. The host **must set DTR**, otherwise the app sends no received frames.
  Reception goes into a 256-B ring. The interrupt routine accepts more at once; there is no NAK.
  The app reads 16 B every 10 ms, so at most 1.6 kB/s. If 256 B or more arrive before the next
  read, everything unread is discarded (`APP_SERIAL_LOST`). A KISS frame with a 256-B IP packet
  is ~275 B long.
- While transmitting, interrupts are masked (~2 s for a full frame). Host writes block for that
  long.
- RF on the USB cable can cause a USB reset at key-up (a ferrite is needed). The port then
  disappears and comes back.
- **Space:** the app uses 3,620 of the 4,096 B overlay. About 470 B remain for extensions.

### 4.2 What AXLink needs for it: TNC profiles

The KISS driver gets a profile per TNC type:

| Profile | Pacing | Particulars |
|---|---|---|
| `generic-kiss` | free; a queue in the TNC is assumed | standard KISS |
| `ackmode` (e.g. NinoTNC, net-sim) | one frame in flight until the `0x0C` echo arrives | exact pacing |
| `f4hwn-kisstnc` (today) | one frame in flight; writes in pieces of ≤ 64 B with ≥ 40 ms gaps; the next frame only after the estimated airtime plus channel access plus a margin | set DTR; send the KISS parameters again after every reconnect; survive USB resets automatically |
| `f4hwn-kisstnc+` (after the firmware extension) | ACKMODE | identification and RSSI per frame |

Plus a **transmit queue with an airtime budget**:

- Priorities: control and small packets (TCP ACKs) before bulk data.
- Drop stale packets instead of sending them.
- Suppress duplicate IP packets in the queue (TCP retransmissions that have not gone out yet).
- Fairness per destination.

At 1200 Bd this gains more than any routing finesse.

For testing we build an **emulator of the KISS app** in front of net-sim (one frame, a 256-B
ring, 16 B per 10 ms, 50-ms slots). Possible later: running the real app logic on the PC. The
app's host test (`test/host_tnc.c`) already runs `app_main` against a mock API; it would have to
become interactive (KISS over TCP, audio through a channel model).

### 4.3 Proposals for the firmware

First in our fork, then as a PR or issue to F4WAT (author of the KISS app) and F4HWN.

| # | Change | Where | Effort (estimate) | Benefit |
|---|---|---|---|---|
| FW1 | KISS ACKMODE (`0x0C`, G8BPQ): keep the tag, send `C0 0C hi lo C0` back after transmitting | KISS app | small, ~50–80 B | exact pacing, no silent drops |
| FW2 | USB back-pressure: re-arm the OUT endpoint only when ≥ 64 B are free in the ring | resident (`usbd_cdc_if.c`, `app_overlay.c`) | small | no ring losses; host writes block instead of losing data. Helps every app. |
| FW3 | Identification and capabilities on a KISS request (e.g. SetHardware `0x06`): name, version, maximum frame, ACKMODE | KISS app | small | AXLink picks the profile itself and notices "app not running" |
| FW4 | RSSI of each received frame to the host | KISS app | small | link quality for the UI and for mesh routing |
| FW5 | A "frame refused" message (RX only, TX blocked) | KISS app | small | the host does not wait in vain |
| FW6 | optional: a second transmit buffer; more than 16 B per read | KISS app | medium (RAM, timing) | more throughput |

For "channel busy" (DCD), Tom M0LTE is working on a KISS extension with the NinoTNC designer,
according to the Packet.NET documentation. We should follow that rather than invent our own
format.

### 4.4 Messenger and AXLink together

- **KISS mode** (radio on the PC): AXLink does IP, chat and station discovery.
- **Messenger mode** (radio on its own): if AXLink chat uses the **APRS message format**
  (APRS 1.0.1 with `{id` acknowledgements), messenger users without a PC can chat with AXLink
  stations. The messenger can be set to any frequency; it ignores IP frames (PID `0xCC`).
- **No IP on 144.800 MHz** (the APRS channel). AXLink needs its own data frequency according to
  the band plan.

## 5. Internet gateway

### 5.1 Terms

| Term | Meaning | Tag |
|---|---|---|
| Station | every AXLink participant (callsign-SSID plus IP) | – |
| Node | a station that forwards for others, by choice | `RELAY` |
| Internet gateway | a node with internet access that shares it with the radio network | `INET` |
| Link gateway | connects distant radio islands over the internet (AXUDP tunnel) | `LINK` |
| Permanent node | runs unattended 24/7, i.e. an automatic station under § 13 AFuV | `AUTO` |

I would avoid "repeater" or "relay" as names: in amateur radio they mean voice repeaters, or the
legal term "Relaisfunkstelle".

### 5.2 Technology

- The gateway announces `INET` and a short summary of its rules (allowed services, rate,
  contact) in station discovery. Clients choose a gateway **deliberately**. The UI shows hops,
  link quality and load.
- Two ways to "share" the internet onto the virtual adapter:
  - **Kernel NAT** (Linux: `ip_forward` plus nftables masquerading): simple. Hard on Windows
    and macOS, and the rules are coarse.
  - **Userspace gateway (recommended):** AXLink ends the radio side in a userspace TCP/IP stack
    (gVisor netstack) and opens an ordinary socket to the internet per connection. Works the
    same on Linux, Windows, macOS and the Pi, without system configuration. Rules per
    connection: destination and port allowlist, quota per callsign, log with the callsign,
    priority.
- Plus a DNS proxy with a cache and an HTTP proxy that **shrinks** pages (text instead of images
  and scripts, compression). At 1200 Bd this is many times more effective than plain NAT.
- Client: "internet over radio" is a switch. Proxy mode (browser and curl use the proxy) is
  better than a default route; otherwise updates, telemetry and cloud sync flood the channel.
- The other direction: devices on a node's LAN/WLAN (e.g. a phone on a Pi hotspot) reach the
  radio network. Same building blocks.

**Orders of magnitude** (estimate, 1200 Bd, the app's defaults): a 256-B packet occupies the
channel for ~2.3 s (267 ms TXDELAY, ~1.9 s frame, channel access). TCP payload reaches roughly
60–90 B/s at best. A 20-KB page then takes ~4 min, a TLS handshake alone ~1 min.

### 5.3 Law in Germany (information only, see the addendum)

Original text from gesetze-im-internet.de, retrieved 2026-11-02, with translations. Not legal
advice.

- § 5 (5) AFuG: „Der Funkamateur darf nur mit anderen Amateurfunkstellen Funkverkehr abwickeln.
  Der Funkamateur darf Nachrichten, die nicht den Amateurfunkdienst betreffen, für und an Dritte
  nicht übermitteln. Satz 2 gilt nicht in Not- und Katastrophenfällen.“ (A radio amateur may
  communicate only with other amateur stations and may not pass messages that do not concern the
  amateur service for or to third parties; the second sentence does not apply in emergencies and
  disasters.)
- § 5 (4) AFuG: no operation "for commercial purposes" and none "for the business provision of
  telecommunication services".
- § 16 (3) AFuV: an amateur station may be connected to telecommunication networks; via a remote
  or automatic station under § 13 only the holder of that station's callsign may provide such
  connections.
- § 16 (7) and (8) AFuV: traffic "in plain language"; transmission methods must allow the
  content to be recovered with generally available technology; „Der Amateurfunkverkehr darf
  nicht zur Verschleierung des Inhalts kodiert oder verschlüsselt werden“ (amateur traffic may
  not be coded or encrypted to obscure its content).
- § 13 (1) and (2) AFuV: operating a remote or automatic station requires a separate callsign
  assignment (bound to a location, with a compatibility study).

My assessment for AXLink at the time:

| Function | Assessment |
|---|---|
| Link gateway (radio islands over the internet, amateur to amateur) | compatible in principle; common practice for packet nodes (AXIP/AXUDP) |
| Amateur-radio services (APRS-IS, DX cluster, radio wikis, HAMNET services) | defensible |
| General browsing, mail with non-amateurs | conflicts with § 5 (5) AFuG |
| HTTPS, TLS or VPN over the air | conflicts with § 16 (8) AFuV |
| Emergencies and disasters | exception from the third-party ban |
| An unattended 24/7 node or gateway | § 13: separate assignment needed |

Further points: everything over the air can be read by anyone, so no logins or passwords over a
gateway. A gateway can be faked (callsigns can be spoofed); signatures (content stays readable)
could protect against that later. Side note: PMR446 is no legal alternative with the UV-K1 or
UV-K5: only type-approved PMR446 radios with a fixed antenna and at most 500 mW ERP are allowed
there; this also concerns the messenger's PMR446 preset for encryption.

The operating profiles proposed here (`HAM-DE` etc.) were dropped by decision D2.

## 6. Tech stack

### 6.1 What decides

- A virtual network adapter on Linux, Windows and macOS.
- A portable internet gateway with rules per connection.
- Running without admin rights (a local SOCKS5/HTTP proxy instead of a driver).
- Robust USB serial handling: resets, recognition by VID/PID, exclusive access.
- One program, simple installers, runs on the Pi, stable for a long time.
- AI-assisted development with few dependencies.

### 6.2 Comparison

| | Go | C#/.NET 10 | Rust |
|---|---|---|---|
| TUN on Linux/Windows/macOS | wireguard-go/tun (MIT; the base of WireGuard-Go and Tailscale) | write it ourselves (P/Invoke for Wintun, utun) | tun-rs |
| Userspace TCP/IP | gVisor netstack (Apache-2.0) | nothing mature | smoltcp (rather embedded) |
| Serial with VID/PID | go.bug.st/serial (BSD-3, Arduino team) | System.IO.Ports; VID/PID per OS ourselves | serialport-rs |
| AX.25/KISS | ourselves (the UI part is small) | Packet.NET (AGPL, young) | ourselves |
| Delivery | one static file, cross-compiling without extra toolchains | self-contained per platform, much larger | one file, cross-compiling with toolchains |
| Pi Zero W (ARMv6) | yes | no (ARMv7 and later) | yes |
| Memory | low | medium | low |
| Long term | the Go 1 compatibility promise | LTS every 3 years (.NET 10 until Nov 2028) | stable (editions) |
| Learning curve, AI suitability | easy | easy | steeper |

### 6.3 Recommendation: Go

Core `axlinkd`: one process with an embedded local web UI, optionally a tray icon. On Windows as
a service (Wintun needs admin rights), on Linux as a systemd service with `CAP_NET_ADMIN`, on
macOS as a launchd service.

- **Written ourselves, small:** KISS (serial and TCP, ACKMODE), AX.25 UI frames including
  segmentation per AX.25 2.2 figure 6.2, IP over AX.25 (PID `0xCC`, ARP `0xCD` optional), the
  destination filter (F1), correct fragmentation (F5). Estimate: 1,500–2,500 lines plus tests.
  This is **not** a new AX.25 stack in the sense of connected mode or NET/ROM.
- **Forwarding (mesh) in userspace**, independent of the operating system's IP forwarding. This
  matters on Windows too.
- **Interop lab:** Packet.NET/pdn, Dire Wolf and LinBPQ as peers; net-sim as the channel.
- **KISS-TCP multiplexer:** other programs (pdn, APRS clients, Winlink/Pat, BPQ) can share the
  radio through AXLink without fighting over the port. Everything goes through the same transmit
  queue.
- **Connected mode / NET/ROM (BPQ interop) later:** pdn as a companion on the multiplexer, or the
  Go output of ax25sdl (AGPL).
- Bonus: a Go core also runs on Android (as with Tailscale). An app for phone plus radio would
  be possible later.

**If you want to stay with C#:** one process; `Packet.Kiss` and `Packet.Ax25` from NuGet (AXLink
then becomes AGPL); our own TUN adapters; no pdn and no pdn-net at runtime. The gateway then
mainly on Linux (nftables), no operation without admin rights.

**Not recommended:** carrying on with pdn plus pdn-net plus RHPv2 as the product base.

### 6.4 Licence

Decide early. Proposal: AGPL-3.0-or-later (fits the packet-net ecosystem and keeps ax25sdl and
Packet.NET code open to us) or GPL-3.0-or-later. Both work with the Apache-2.0, MIT and BSD
libraries above. The firmware is a separate program. (Decided: GPL-3.0-or-later, D5.)

## 7. Target architecture (sketch)

```text
 browser UI (local)                ordinary programs (curl, browser, servers)
          │ HTTP/WebSocket                    │ sockets
          ▼                                   ▼
┌──────────────────────────── axlinkd (one process) ──────────────────────────────┐
│ UI/API │ station discovery │ chat (APRS format) │ gateway rules │ profiles          │
│ routing table and forwarding (userspace)                                          │
│ IP bridge: PID 0xCC/0xCD, destination filter, fragmentation, broadcast filter      │
│ TUN (wireguard-go/tun)   or   netstack (without admin rights / gateway)            │
│ transmit queue: airtime budget, priorities, duplicates, pacing per TNC            │
│ KISS serial/TCP │ TNC profiles │ KISS-TCP multiplexer │ AXUDP (link gateway)       │
└───────────────────────────────────────────────────────────────────────────────────┘
          │ USB-CDC                                   │ internet (gateways only)
          ▼                                           ▼
   UV-K1 / UV-K5 V3 with the KISS app          AXUDP peers, internet destinations
```
